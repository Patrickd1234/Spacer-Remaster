# Spacer codebase fit for GitHub-commit task automation

Scope: what the Spacer codebase (React 19 + Supabase, `Spacer-reMastered/Spacer-app`) already has, and lacks, for letting GitHub commits move tasks. Local code investigation only; nothing was modified. All paths are relative to `Spacer-reMastered/`. "Source" links point at local files with line numbers.

Important caveat on the schema snapshot: `Spacer-app/supabase/schema/schema.sql` is dated 12 Nov 2026 13:30 (file mtime) and is generated by `scripts/dump-schema.mjs` (header, lines 1-3). It **predates** four later migrations: `20261112110000_rbac_rules` (applied 13 Nov), `20261113090000_activity_log_organization` (applied 14 Nov), `20261114090000_assign_roles` (applied 17 Nov) and `20261119090000_meetings` (NOT applied yet) — per `DEVELOPMENT_LOG.md` lines 172-233. So for RBAC tables, `activity_log.organization_id` and the converted helper functions, the migration files are the source of truth, not the snapshot (the snapshot has no `rbac_*` tables at all).

## 1. Task identity: what would a developer type in a commit message today?

### Takeaway
Tasks are identified only by a random UUID; there is no human-readable key (no `SPC-123`), no per-project or per-org counter, and no project key/prefix column. Today the only stable reference a developer could paste into a commit is the full UUID (e.g. copied from the `?task_id=<uuid>` deep link), which is impractical — a short key would have to be added.

### Cited Findings
- `tasks.id uuid default gen_random_uuid() not null`; other columns: `organization_id`, `project_id` (nullable: "unfiled"/general tasks), `milestone_id`, `title`, `description`, `status`, `priority`, `due_date`, `assignee_id`, `created_by`, `created_at`, `updated_at`, `parent_task_id`, `search_vector`, `sub_tasks text`, `column_id`, `sprint_id`, `story_points`, `completed_at`. No number/key column. — [schema.sql:341-362](Spacer-app/supabase/schema/schema.sql)
- `tasks_pkey PRIMARY KEY (id)` is the only key on tasks; no unique constraint on any other column. — [schema.sql:460](Spacer-app/supabase/schema/schema.sql)
- `project_spaces` columns: `id uuid`, `team_space_id`, `name`, `status`, `created_at`, `search_vector`, `team_lead`, `due_date`. No `key`/`prefix`/`slug`/counter column. — [schema.sql:302-311](Spacer-app/supabase/schema/schema.sql)
- `organizations` has only `id`, `name`, `created_at`. — [schema.sql:267-271](Spacer-app/supabase/schema/schema.sql)
- A grep of `src/`, `supabase/migrations/` and `supabase/schema/` for `task_number|task_key|short_id|project_key|prefix|"SPC` returned nothing; a grep for `id.slice`/`id.substring` in `src/` (a shortened-UUID display) also returned nothing. — (search over [Spacer-app/src](Spacer-app/src), [Spacer-app/supabase](Spacer-app/supabase))
- The only externally visible task reference is the deep link `/project_page/<project_id>?task_id=<task uuid>`, built for notifications and read by the project page. — [notifications.js:96](Spacer-app/src/notifications.js); [project_page.jsx:683](Spacer-app/src/project_page.jsx); route [App.jsx:245](Spacer-app/src/App.jsx)
- Tasks with `project_id IS NULL` exist (general/unfiled tasks; index `tasks_org_general_idx ... WHERE (project_id IS NULL)`), so a per-project key alone would not cover every task. — [schema.sql:762](Spacer-app/supabase/schema/schema.sql)

### Inferences
- A design needs a new identifier: e.g. `project_spaces.key` (short uppercase prefix, unique per organization) plus `tasks.number` (per-project or per-org sequence assigned by a BEFORE INSERT trigger with a lock/counter row), and a decision for unfiled (`project_id IS NULL`) tasks (org-level prefix, or not addressable from commits).
- Existing tasks would need a backfill of numbers; the board UI, task detail, search (`search_vector`) and notifications would need to display the key so developers can find it.
- Matching full UUIDs in commit messages would work without schema change but is a poor UX; a UUID-prefix match is not supported by any index.

### Gaps
- No product decision found on key format (per project vs per org) — needs a user decision.

## 2. Task statuses and subtask-derived status

### Takeaway
Status is a plain text column constrained to exactly `todo`, `in_progress`, `done`. An "In Review" status is planned (user confirmed) but not built; custom board columns (including a suggested "Review" column) map onto the three base statuses. Subtask-derived status is computed only in the browser, not in the database.

### Cited Findings
- `tasks.status text default 'todo'` with `tasks_status_check CHECK (status = ANY (ARRAY['todo','in_progress','done']))`. — [schema.sql:348](Spacer-app/supabase/schema/schema.sql), [schema.sql:548](Spacer-app/supabase/schema/schema.sql)
- Custom per-project columns: `project_columns.base_status` is checked to `('todo','in_progress','done')`; moving a card sets both `tasks.column_id` and `tasks.status`; a project without rows shows default Backlog / Doing / Done. — [20261026100000_project_columns.sql:1-15](Spacer-app/supabase/migrations/20261026100000_project_columns.sql); defaults [projectColumns.js:7-20](Spacer-app/src/projectColumns.js)
- A task's column is its saved `column_id` only if that column's `base_status` still equals `task.status`; otherwise the first column with that status ("status can change via subtasks"). — [boardGrouping.js:13-19](Spacer-app/src/boardGrouping.js)
- Column suggestions include `{ name: "Review", baseStatus: "in_progress" }` — so "Review" today can only be a custom column whose status is `in_progress`. — [BoardColumns.jsx:136-143](Spacer-app/src/components/BoardColumns.jsx)
- Planned: "Add an 'In Review' task status ... user confirmed. Not built yet; planned for the All Tasks phase", and "In Review status migration touching tasks_status_check and every status consumer". — [memory: spacer-ui-doc-implementation.md:16, :32](C:/Users/DELL/.claude/projects/c--Users-DELL-OneDrive-Desktop-main-spacer/memory/spacer-ui-doc-implementation.md). No `in_review` string exists anywhere in `src/`, migrations or docs (grep).
- Display names: `STATUS_NAMES = { todo: "Backlog", in_progress: "Doing", done: "Done" }`. — [activityLabels.js:3](Spacer-app/src/activityLabels.js)
- `statusFromSubtasks(subtasks)`: null when no subtasks, `done` if all done, `in_progress` if some done, else `todo`. Subtasks are a JSON string in `tasks.sub_tasks` (`[{ text, done }]`). — [taskStatus.js:1-19](Spacer-app/src/taskStatus.js)
- It is applied client-side when subtasks are edited: `newStatus = statusFromSubtasks(newSubtasks) ?? task.status`, then `update({ sub_tasks, status })`. — [project_page.jsx:321-347](Spacer-app/src/project_page.jsx); same in [CalendarView.jsx:67](Spacer-app/src/CalendarView.jsx)
- `completed_at` is set/cleared by the BEFORE trigger `tasks_sprint_rules` whenever status becomes / leaves `done` (no auth dependency for this part). — [schema.sql:1948-1955](Spacer-app/supabase/schema/schema.sql)

### Inferences
- A commit that sets a task with unfinished subtasks to `done` will be silently reverted to `in_progress`/`todo` the next time anyone toggles a subtask in the UI (client recomputes from subtasks). The design must decide: mark all subtasks done, refuse, or only move tasks without subtasks.
- If the automation moves status server-side, it should also clear or re-point `tasks.column_id` (or leave it; `columnKeyForTask` will fall back to the first column of the new status). A "move to In Review" keyword can today only mean `in_progress` (+ optionally a specific custom column), unless the planned `in_review` status migration lands first — that migration touches `tasks_status_check`, `project_columns.base_status`, `STATUS_NAMES`, `statusFromSubtasks`, `team_space_stats`, Reports, etc.

### Gaps
- Did not enumerate every status consumer (Reports, Home, `team_space_stats` refresh) that would need change for an `in_review` status.

## 3. Who may change status under RLS

### Takeaway
Any signed-in user who can edit the project (`project.edit` in its department, or being a direct `project_members` row) may update any task in it, including status; unfiled tasks may be updated by anyone in the organization. All of this is bypassed by the service role, so an edge function using the service key must enforce its own authorization (and MFA is irrelevant to it).

### Cited Findings
- `tasks_update` policy: `USING ((project_id IS NULL AND organization_id = current_org_id()) OR (project_id IS NOT NULL AND can_edit_project(project_id)))`, same `WITH CHECK` plus `organization_id = current_org_id()`. — [schema.sql:2702-2704](Spacer-app/supabase/schema/schema.sql) (not altered by later migrations; `rbac_rules` only alters `tasks_delete`, [20261112110000_rbac_rules.sql:367-368](Spacer-app/supabase/migrations/20261112110000_rbac_rules.sql))
- Restrictive `mfa_required` policy on tasks for `authenticated` (`mfa_satisfied()`, which reads `auth.jwt() ->> 'aal'`). — [schema.sql:2689-2691](Spacer-app/supabase/schema/schema.sql), [schema.sql:1460-1470](Spacer-app/supabase/schema/schema.sql)
- `can_edit_project(p)` = project exists and (`has_permission('project.edit', ps.team_space_id)` or `is_project_member(ps.id)`); `can_manage_project` = `has_permission('project.manage', ...)`. — [20261112110000_rbac_rules.sql:49-75](Spacer-app/supabase/migrations/20261112110000_rbac_rules.sql)
- `has_permission()` resolves via `memberships` for `auth.uid()` and `current_org_id()` (= `users.organization_id` of `auth.uid()`), so it returns false when `auth.uid()` is null. — [20261112100000_rbac_foundation.sql:140-162](Spacer-app/supabase/migrations/20261112100000_rbac_foundation.sql); [schema.sql:1058-1065](Spacer-app/supabase/schema/schema.sql)
- Deadline changes are additionally restricted by `tasks_guard_due_date` (managers only) — but only `if auth.uid() is not null`. Sprint membership changes are restricted by `tasks_sprint_rules` — also only when `auth.uid() is not null`. — [20261112110000_rbac_rules.sql:160](Spacer-app/supabase/migrations/20261112110000_rbac_rules.sql); [schema.sql:1855-1875](Spacer-app/supabase/schema/schema.sql), [schema.sql:1968-1973](Spacer-app/supabase/schema/schema.sql)
- Edge functions doc their own rule: "Functions that act with the service role must enforce two-factor themselves: RLS ... doesn't apply to the service role." — [_shared/mfa.ts:18-20](Spacer-app/supabase/functions/_shared/mfa.ts)

### Inferences
- A webhook function cannot act "as" a GitHub user via RLS (no Spacer JWT). Options: (a) service role + explicit checks in code (e.g. the mapped committer must pass `can_edit_project` — not callable as them without a JWT; would need a SECURITY DEFINER SQL function taking a user id, e.g. a new `user_can_edit_project(user_id, project_id)`), or (b) a SECURITY DEFINER RPC `apply_commit_transition(...)` that does the checks and the update in one place. Existing helpers are all hard-wired to `auth.uid()`.
- Simplest safe rule consistent with today's model: only move tasks in the project(s) linked to the repository the webhook came from (repo-to-project binding is the authorization), and optionally require the commit author to map to an org member with edit rights.

### Gaps
- No existing helper evaluates permissions for an arbitrary user id; would need to be added.

## 4. Side effects of a status change today, and behaviour with auth.uid() = null

### Takeaway
Status changes trigger: an automatic `activity_log` "updated" row (trigger), an in-app notification to the task creator (trigger), `completed_at` maintenance, and department stats refresh. The friendly "status_changed" activity row is written by the **app**, not the database. No email is sent on status change. A service-role update would succeed, but its trigger-written activity row would have `actor_id = NULL` and `organization_id = NULL`, which makes it invisible to everyone.

### Cited Findings
- Triggers on `tasks`: `tasks_column_matches_project` (BEFORE), `tasks_email_assignee_on_insert/update` (AFTER, only on assignee change → `dispatch_edge_webhook('send-notification')`), `tasks_guard_due_date` (BEFORE UPDATE OF due_date), `tasks_log_activity_trigger` (AFTER INSERT OR UPDATE), `tasks_notify_trigger` (AFTER INSERT OR UPDATE), `tasks_refresh_stats_trigger`, `tasks_set_updated_at`, `tasks_sprint_rules` (BEFORE INSERT OR UPDATE OF status, sprint_id, project_id). — [schema.sql:2229-2245](Spacer-app/supabase/schema/schema.sql)
- `tasks_log_activity()` (SECURITY DEFINER) inserts `('task', new.id, auth.uid(), 'updated', to_jsonb(old), to_jsonb(new))` on any non-quiet update (quiet: `sprint_id, story_points, completed_at, updated_at, search_vector`). It never writes `status_changed`. — [schema.sql:1877-1895](Spacer-app/supabase/schema/schema.sql)
- The app writes `action: "status_changed"` rows itself, with `actor_id` = session user and `new_state: { project_id, title, status }`, after board drag ([project_page.jsx:515-521](Spacer-app/src/project_page.jsx)), subtask edits ([project_page.jsx:346-355](Spacer-app/src/project_page.jsx)) and in the calendar ([CalendarView.jsx:95](Spacer-app/src/CalendarView.jsx), [:148](Spacer-app/src/CalendarView.jsx)). `projectActivity.js` dedupes the double rows ("The database logs every task insert and update itself ... while the app also logs its own ... status_changed"). — [projectActivity.js:1-10](Spacer-app/src/projectActivity.js)
- Labels: `task:status_changed` → "Moved “title” to Done"; header bell feed shows `status_changed` as "<actor> updated <subject>". — [activityLabels.js:14](Spacer-app/src/activityLabels.js); [header.jsx:193-194](Spacer-app/src/partials/header.jsx); project page rendering [project_page.jsx:1061](Spacer-app/src/project_page.jsx)
- `activity_log_insert` policy: `WITH CHECK (actor_id = auth.uid())` for `authenticated` (service role bypasses). — [schema.sql:2323-2324](Spacer-app/supabase/schema/schema.sql)
- `activity_log_set_organization()` BEFORE INSERT trigger: if `current_user in ('authenticated','anon')` → org = `current_org_id()`; else, if org is null → `coalesce(current_org_id(), actor's users.organization_id)`. Comment: "For database functions and edge functions (service role) it is the caller's organization, else the actor's." — [20261113090000_activity_log_organization.sql:30-51](Spacer-app/supabase/migrations/20261113090000_activity_log_organization.sql)
- `activity_log_select` now requires `organization_id = current_org_id()` and `can_see_activity(actor_id, ...)`. — [20261113090000_activity_log_organization.sql:98-106](Spacer-app/supabase/migrations/20261113090000_activity_log_organization.sql)
- `can_see_activity()` returns false unless the actor is a user in the reader's org (`select 1 from users where id = p_actor_id and organization_id = current_org_id()`); with `p_actor_id` NULL neither branch is true. — [schema.sql:859-893](Spacer-app/supabase/schema/schema.sql)
- `tasks_notify()` on status change: `notify_user(old.created_by, 'status_change', 'task', new.id, '"' || title || '" moved to ' || new.status)` — raw status code, no actor name; skipped if `created_by` is null. Assignment messages use `coalesce(v_actor_name, 'Someone')`. — [schema.sql:1898-1927](Spacer-app/supabase/schema/schema.sql)
- `notify_user()` just inserts into `notifications` (no auth dependency). — [schema.sql:1475-1488](Spacer-app/supabase/schema/schema.sql)
- `tasks_sprint_rules`: sets `completed_at` on → done, clears on ← done; permission check gated on `auth.uid() is not null`. — [schema.sql:1948-1976](Spacer-app/supabase/schema/schema.sql)
- `tasks_refresh_stats` → `refresh_team_space_stats(team_space_id)`; no auth dependency. — [schema.sql:1929-1946](Spacer-app/supabase/schema/schema.sql)
- Email webhook (`dispatch_edge_webhook`) fires only on assignee insert/change, not status. — [20261031100000_notifications.sql:68-76](Spacer-app/supabase/migrations/20261031100000_notifications.sql)
- `tasks` is in the `supabase_realtime` publication, so open boards receive server-side updates. — [schema.sql:2944](Spacer-app/supabase/schema/schema.sql)
- `comments` (possible place to record "referenced in commit abc123"): `comments_insert` requires `author_id = auth.uid()`; `comments_notify` uses `auth.uid()` for the actor name and skips mentions when `u.id != new.author_id` is NULL (author null). — [schema.sql:105-111](Spacer-app/supabase/schema/schema.sql), [schema.sql:963-988](Spacer-app/supabase/schema/schema.sql), [schema.sql:2411-2412](Spacer-app/supabase/schema/schema.sql)

### Inferences
- Nothing breaks (no trigger raises) on a service-role status update: the two auth-gated checks are skipped by design, `completed_at`/stats/notification still work.
- But the audit trail degrades: the trigger's 'updated' row gets `actor_id NULL`; because `tasks_log_activity` is SECURITY DEFINER, `current_user` inside the insert is the function owner (not `authenticated`), so the org falls to `coalesce(current_org_id() = NULL, actor org = NULL)` → `organization_id NULL` → hidden from every reader. The automation should therefore insert its own `activity_log` row (service role) with explicit `organization_id` (= task's org), `action 'status_changed'`, `new_state {project_id, title, status, source:'github', commit sha/url}`, and `actor_id` = the mapped Spacer user (else it is invisible via `can_see_activity`). Alternatively the update could run inside an RPC that sets `request.jwt.claims`/a session variable — more invasive.
- The creator's bell message will say `moved to done` (raw code), and assignment-style texts would say "Someone". A design may want `tasks_notify` to say "via GitHub".
- The dedupe in `projectActivity.js` keys on same task + same actor within 60 s; a bot row with a different/null actor will not be merged with the trigger row (the trigger row is hidden anyway).

### Gaps
- Did not verify the exact `current_user` inside nested SECURITY DEFINER triggers on the live DB; the inference follows PostgreSQL semantics (security definer switches `current_user` to the owner) and the trigger's own comment ("Not security definer, so current_user is the role doing the insert", [activity_log_organization.sql:30](Spacer-app/supabase/migrations/20261113090000_activity_log_organization.sql)). A dry-run would confirm.

## 5. Existing edge functions, auth patterns, CORS, secrets

### Takeaway
Ten Deno edge functions exist; none relate to GitHub. Two are webhook receivers authenticated by a shared `x-webhook-secret` (constant-time compare, `_shared/webhookAuth.ts`); the rest act for a signed-in caller using their JWT plus a service-role client. `config.toml` declares no per-function `verify_jwt` settings. Secrets are Supabase function secrets (`Deno.env`) plus two Vault secrets read by SQL. There is no HMAC-signature verifier (what GitHub webhooks use) and no edge-function tests.

### Cited Findings

### Inferences
- `dispatch_edge_webhook` sends no `Authorization` header, yet emails are delivered on live, so `send-notification` must be deployed with JWT verification disabled on live (not recorded in `config.toml`). A GitHub webhook receiver also cannot send a Supabase JWT, so the new function needs `verify_jwt = false` — best declared in `config.toml` as `[functions.github-webhook] verify_jwt = false` so it is versioned.
- `webhookAuth.ts` compares a static header; GitHub instead signs the body (HMAC-SHA256 in `X-Hub-Signature-256`), so a new shared helper is required (verify against the raw body before `req.json()`), reusing the constant-time compare idea. A per-organization webhook secret would have to be stored somewhere (Vault entry per org or an encrypted column) — nothing exists for per-org secrets today; Vault currently holds only two global secrets.
- The webhook needs no CORS (server-to-server); the shared `cors.ts` can be skipped.

### Gaps
- Live deploy flags (`--no-verify-jwt`) per function are not recorded anywhere in the repo; would need checking in the Supabase dashboard.

## 7. RBAC: which permission governs "manage integrations"?

### Takeaway
RBAC is a fixed role → permission table (`rbac_roles`, `rbac_permissions`, `rbac_role_permissions`) checked by `has_permission(key, department)`. No integration permission exists. The closest existing ones are `organization.update` ("Rename the organization and change its settings", org-scope) for connecting GitHub to the org, and `project.manage` ("Change a project's settings ...", department-scope) for linking a repo to a project. The documented process for a new key (e.g. `integration.manage`) is a migration inserting it and granting it.
