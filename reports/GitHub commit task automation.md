# Let GitHub merges move Spacer's tasks

**Yes, Spacer can move tasks automatically from GitHub, and the safest way to build it is a signed GitHub webhook going to a new Supabase Edge Function, not a GitHub Actions workflow.** GitHub already sends a `push` event and a `pull_request` event that tells you whether a PR was merged. A function with `verify_jwt = false` can check the HMAC signature, find task keys in the branch name, PR title, PR body and commit messages, and move the task. Jira, Linear, Shortcut, ClickUp and Plane all work this way: a short `PREFIX-NUMBER` key, a "closing word" such as *fixes*, and a rule that only a merge into the default branch marks a task Done. Spacer cannot do this today, for three concrete reasons. Tasks have only a random UUID, so there is nothing short for a developer to type. There is nowhere to store a secret per organization. And a status change made with the service role produces an activity row with no actor and no organization, which nobody can see. The recommended design has four phases. First add short task keys. Then ship an org-level webhook with fixed defaults: PR opened → In Progress, merged to default → Done, forward-only. Then add identity linking and In Review. Only later move to a GitHub App, once you have several customer organizations or want Spacer to comment back on PRs. Five product decisions block the build, and they are listed at the end.

## GitHub already sends everything Spacer needs

Spacer can learn about a developer's work from GitHub in three ways, and they differ mostly in who sets them up and who holds the secret. In the first, **a GitHub Actions workflow in each repo** posts the event JSON to Spacer. It works, but it needs a YAML file and a secret in every repo. To react to merges you have to list `pull_request` type `closed` and check `github.event.pull_request.merged == true`, because merges are not among the default trigger types ([GitHub Docs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)). PRs from forks never receive the secret ([GitHub Docs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)). Worse, the body Actions sends is not signed by GitHub, so anyone holding the bearer token can forge any payload. Cost is not the problem: a curl job takes under a minute, and a 2-core Linux runner costs **$0.006/min** against monthly included credit of $12 on Free and $18 on Team ([GitHub Docs: billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)).

In the second, **a repository or organization webhook** posts the event straight to Spacer. An admin pastes a URL and a secret once, and an org-level hook covers every current and future repo. Each delivery carries `X-Hub-Signature-256`, an HMAC-SHA256 of the raw body computed with the shared secret ([GitHub Docs: validating deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)), plus a unique `X-GitHub-Delivery` ID for deduplication. GitHub expects **a response within 10 seconds** and **does not retry failed deliveries automatically**. You list and redeliver failures yourself through the REST API ([GitHub Docs: best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks); [GitHub Docs: failed deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries)).

In the third, **a GitHub App** installs in one click on chosen repos and uses one central webhook secret. It mints installation tokens that expire after an hour, which the app can use to comment on PRs and to call the redelivery API ([GitHub Docs: installation tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)). In exchange you register the app, sign RS256 JWTs with a private key that expire within 10 minutes, and build an install callback ([GitHub Docs: app JWT](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app)). The research notes estimate this at one to three extra days of work. That is a judgment, not a vendor figure.

| Path | Setup by customer | Payload authenticity | Write-back to GitHub | Best use for Spacer |
|---|---|---|---|---|
| Actions workflow | YAML + secret per repo | Bearer token only (forgeable by token holder) | No | Fallback when no one has org-admin rights |
| Org/repo webhook | Paste URL + secret once per org | GitHub HMAC signature | No (no token) | **MVP / v1** |
| GitHub App | One-click install | GitHub HMAC signature, one app secret | Yes (PR comments, redelivery) | v2, once several orgs or write-back are wanted |

The Edge Function side is straightforward. Supabase documents `[functions.<name>] verify_jwt = false` for providers that cannot send a Supabase JWT, and uses Stripe webhooks as its example ([Supabase Docs: function configuration](https://supabase.com/docs/guides/functions/function-configuration)). Deno's own webhook example reads the raw bytes first and verifies with `crypto.subtle.verify`, so the comparison runs in constant time ([Deno Docs](https://docs.deno.com/examples/http_server_webhooks/)). The function's limits are 2 s of CPU per request and a 150 s wall clock on Free ([Supabase Docs: limits](https://supabase.com/docs/guides/functions/limits)). That is plenty, as long as the function verifies, stores the delivery, returns 202, and does the processing in `EdgeRuntime.waitUntil` or a database-triggered worker ([Supabase Docs: background tasks](https://supabase.com/docs/guides/functions/background-tasks)).

## Five vendors agree on a key, a closing word and the default branch

The market has settled on one convention, so Spacer does not need to invent one. Jira wants `JRA-123` in the branch name, the commit message or the PR title, in capitals ([Atlassian](https://support.atlassian.com/jira-software-cloud/docs/reference-issues-in-your-development-work/)). Linear links any branch or PR that contains `ENG-123`, but it acts on commits only when a magic word comes before the ID ([Linear Docs](https://linear.app/docs/github)). Shortcut uses `sc-123` in branches and `[sc-123]` in commits and PRs ([Shortcut Help](https://www.shortcut.com/help/integrations/github)). ClickUp accepts `CU-abc123` and an inline status command, `#id[status]`; its help center could not be fetched, so this is less verified ([ClickUp](https://help.clickup.com/hc/en-us/articles/6305771568791-GitHub)). Asana is the outlier and a warning. It has no short key, so its official Action has to find a full task URL in the PR description ([GitHub Marketplace](https://github.com/marketplace/actions/attach-pull-request-to-asana-task)), and third-party guides name matching as the integration's weak point ([Nira](https://nira.com/asana-github-integration/)).

| Tool | Task reference | What moves status | Default mapping / configurability |
|---|---|---|---|
| Jira | `JRA-123` (uppercase) in branch, commit, PR title | Smart Commit `#transition` commands, or an automation rule "PR merged → Transition" | No implicit mapping; admins build rules ([Atlassian Smart Commits](https://support.atlassian.com/jira-software-cloud/docs/process-issues-with-smart-commits/)) |
| Linear | `ENG-123` in branch, PR title/body; commits need a magic word | Closing words (close/fix/resolve/complete/implement + tenses) | Per team: PR open → In Progress, merged → Done; per-target-branch rules ([Linear Docs](https://linear.app/docs/github)) |
| Shortcut | `sc-123` / `[sc-123]` | Event handlers per VCS event; commit verbs | Admin-mapped, **forward-only** ([Shortcut Help](https://www.shortcut.com/help/integrations/github)) |
| ClickUp | `CU-id`, `#id`, custom ID | `#id[status]` in commit, branch or PR | Status named inline ([ClickUp](https://clickup.com/integrations/github)) |
| Asana | Task URL in PR description | Attaches a PR-status widget; completion not documented | Action with `ASANA_SECRET` repo secret ([Marketplace](https://github.com/marketplace/actions/attach-pull-request-to-asana-task)) |
| GitHub/GitLab native | `#123` | Closing keywords on merge to **default branch only** | Fixed ([GitHub Docs](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue); [GitLab Docs](https://docs.gitlab.com/user/project/issues/managing_issues/)) |

Two design lessons fall out of the comparison. **First, drive status from PR events and treat commits as a secondary signal.** Linear and Plane let admins map each PR state (opened, review requested, merged) to a status, Plane per project ([Plane Docs](https://docs.plane.so/integrations/github)). Jira's Smart Commits show the cost of commit commands: force-pushes and squash merges can replay them so they "appear duplicated", and a transition "will silently fail" when the workflow has required fields ([Atlassian Smart Commits](https://support.atlassian.com/jira-software-cloud/docs/process-issues-with-smart-commits/)). GitLab users report that squash merges drop the "Closes" line and leave issues open ([GitLab issue 285300](https://gitlab.com/gitlab-org/gitlab/-/issues/285300)). **Second, make closing deliberately hard.** GitHub ignores closing keywords on PRs that target a non-default branch ([GitHub Docs](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)). Linear changes status only when the *last* linked PR is merged, and it supports `skip`/`ignore` to stop a link ([Linear Docs](https://linear.app/docs/github)). Even so, people accidentally close issues by writing "fix" in a commit ([GitHub Community](https://github.com/orgs/community/discussions/66741)). Two things remain unknown: no vendor documents whether reverting a merge reopens a task, and none documents how fork PRs are treated. Spacer should therefore decide these behaviours explicitly rather than inherit them.

The reliability trick that matters most is the "copy branch name" button that Linear and Jira ship. Linear generates the branch name with Cmd/Ctrl+Shift+. and can also move the issue to started and self-assign it ([Linear Docs](https://linear.app/docs/github)). With that button, developers never type the key by hand, and matching on branch name becomes close to foolproof.

## The webhook is a public endpoint, so the signature and the repo binding must do the authorizing

A webhook function with JWT verification turned off can be called by anyone on the internet, so every authorization decision has to come from the signature and from Spacer's own data. **Verify `X-Hub-Signature-256` over the raw bytes before parsing JSON.** Never compare with `==`, and make sure no proxy rewrites the body ([GitHub Docs](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)). GitHub publishes a test vector to unit-test the verifier against: secret `It's a Secret to Everybody`, payload `Hello, World!`, expected `sha256=757107ea…3e17`. The function must pick the organization's secret *before* it has verified anything. The right key for that lookup is a random, non-secret endpoint ID in the URL path (or the `X-GitHub-Hook-ID` header captured during setup). The repository name in the unverified body must not be used for it. GitHub explicitly advises never putting credentials in the payload URL, and a lookup ID is not a credential ([GitHub Docs: best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)).

**The per-organization HMAC secret cannot be hashed**, because the function needs the plaintext to recompute the signature. It belongs in Supabase Vault, which encrypts with libsodium AEAD using a key held outside the database. Anyone who can read the `vault.decrypted_secrets` view can read every secret, so only a locked-down `SECURITY DEFINER` function should touch it ([Supabase Docs: Vault](https://supabase.com/docs/guides/database/vault)). Spacer already uses exactly this pattern: `dispatch_edge_webhook()` reads two global Vault secrets, with execute revoked from `anon` and `authenticated` ([notifications migration](../Spacer-app/supabase/migrations/20261031100000_notifications.sql)). If you also offer the Actions fallback, its bearer tokens are high-entropy, so store them only as SHA-256 hashes and show them once. Rotation should keep the old and new secret valid together for a 24–72 hour grace window, because the admin has to paste the new value into GitHub by hand.

GitHub signatures carry no timestamp, so **a unique constraint on `X-GitHub-Delivery` is the only replay defence.** GitHub reuses the same ID on redelivery precisely so you can detect duplicates ([GitHub Docs](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)). Keep delivery IDs for 30–90 days. Bind each organization to an explicit list of numeric `repository.id` values. Do not use `full_name`, which changes on rename or transfer. For deliveries from repos not on the list, return 202 and do nothing. Treat commit author names and emails as forgeable display text, because they come from local git config. Attribution should use the authenticated `sender`, `pusher` or `pull_request.merged_by` login, matched to a Spacer member through a verified link. Finally, bound the work: cap the body size, cap the task keys parsed per message at about 20, parse with a regex anchored to the organization's own prefix, and pass values only through parameterized RPCs. Supabase documents no built-in rate limiting for functions called without a JWT, so put a cheap per-endpoint counter in Postgres after the HMAC check.

One Spacer-specific hazard deserves emphasis. **The service role bypasses RLS, and Spacer's guard triggers deliberately skip their checks when `auth.uid()` is null.** Both `tasks_guard_due_date` and `tasks_sprint_rules` work this way ([rbac_rules migration](../Spacer-app/supabase/migrations/20261112110000_rbac_rules.sql); [schema.sql](../Spacer-app/supabase/schema/schema.sql)). The codebase already documents that service-role functions must enforce their own rules ([_shared/mfa.ts](../Spacer-app/supabase/functions/_shared/mfa.ts)). All privileged logic should therefore live in one narrow `SECURITY DEFINER` RPC, for example `apply_github_event(org_id, …)`. That RPC re-checks that each task belongs to the organization and to a project linked to the sending repo, so the edge function never touches `tasks` directly.

## Spacer is missing the task key, a secret store and a visible actor

Spacer's codebase has a webhook culture to build on, but none of the pieces specific to GitHub. **Tasks are identified only by `id uuid`.** There is no number column and no key, and `project_spaces` and `organizations` have no prefix column either ([schema.sql](../Spacer-app/supabase/schema/schema.sql)). The only external reference is the deep link `?task_id=<uuid>` ([notifications.js](../Spacer-app/src/notifications.js)). Tasks with `project_id IS NULL` (unfiled) also exist, so a key scoped only to projects would leave some tasks unaddressable.

**Status is a three-value check constraint: `todo`, `in_progress`, `done`.** Custom board columns map onto those three values. "Review" can exist today only as a custom column whose base status is `in_progress` ([project_columns migration](../Spacer-app/supabase/migrations/20261026100000_project_columns.sql); [BoardColumns.jsx](../Spacer-app/src/components/BoardColumns.jsx)). A real In Review status has been approved but not built. It would touch `tasks_status_check`, `project_columns.base_status`, `STATUS_NAMES`, `statusFromSubtasks` and the stats code ([UI plan memory](C:/Users/DELL/.claude/projects/c--Users-DELL-OneDrive-Desktop-main-spacer/memory/spacer-ui-doc-implementation.md)). Subtasks create a trap. The browser recomputes status from subtasks whenever one is toggled ([taskStatus.js](../Spacer-app/src/taskStatus.js); [project_page.jsx](../Spacer-app/src/project_page.jsx)). So if a merge sets a task with open subtasks to Done, the next subtask click silently moves it back to Doing.

**Side effects are the subtlest gap.** A service-role update still fires the `completed_at` maintenance, the stats refresh, realtime updates to open boards, and the creator's bell notification. But the bell text is the raw code, "moved to done", with no actor ([schema.sql](../Spacer-app/supabase/schema/schema.sql)). The `tasks_log_activity` trigger writes an "updated" row with `actor_id = NULL`. Because that trigger is `SECURITY DEFINER`, the organization trigger cannot resolve an organization either, so the row is stored with `organization_id = NULL`. `activity_log_select` requires a matching organization, and `can_see_activity()` requires the actor to be in the reader's organization, so **every reader is blocked from that row** ([activity_log_organization migration](../Spacer-app/supabase/migrations/20261113090000_activity_log_organization.sql)). That conclusion follows from PostgreSQL semantics; it has not been confirmed on the live database, and a dry-run should check it. The friendly "Moved 'title' to Done" entry is written by the app, not the database ([projectActivity.js](../Spacer-app/src/projectActivity.js); [activityLabels.js](../Spacer-app/src/activityLabels.js)). The automation must therefore write its own `status_changed` row with an explicit `organization_id` and a visible actor.

Settings and RBAC are greenfield. The Connected Apps tab shows a disabled "GitHub Sync — Link PRs & commits to tasks" Coming Soon card ([Settings.jsx](../Spacer-app/src/Settings.jsx)). The earlier fake GitHub OAuth popup was deleted as a spoofing risk ([SECURITY_AND_FIXES_LOG.md](../Spacer-app/docs/SECURITY_AND_FIXES_LOG.md)). Apart from the organization name, workspace settings live only in `localStorage`. No permission covers integrations. The nearest are `organization.update` (organization scope) and `project.manage` (department scope), and new keys must be inserted and granted explicitly in a migration ([RBAC.md](../Spacer-app/docs/RBAC.md)). The existing `_shared/webhookAuth.ts` compares a static header in constant time, but GitHub signs the body, so a new HMAC helper is needed ([webhookAuth.ts](../Spacer-app/supabase/functions/_shared/webhookAuth.ts)). The repo also has no `[functions.*]` blocks in `config.toml`, so the `verify_jwt` settings currently used on live are not under version control ([config.toml](../Spacer-app/supabase/config.toml)).

| Task keys | Organization (or project) prefix column, `tasks.number` assigned by a BEFORE INSERT trigger with a counter row, backfill, display on card/detail/search, "Copy branch name" button | Covers unfiled tasks if numbering is per organization |

## Recommended design: org webhook first, GitHub App later

The recommendation is an **organization-level GitHub webhook going to a per-organization endpoint URL**, verified with HMAC against a Vault-stored secret. Subscribe only to `push` and `pull_request`. The mapping copies Linear's defaults and Shortcut's forward-only rule. A PR opened from a branch, or with a title, that contains `SPC-123` links the task and moves it to In Progress. A PR **merged into the default branch** moves it to Done, but only once every linked PR is merged. A PR closed without merging changes nothing, and tasks never move backward automatically. Commits pushed straight to the default branch move a task only when a closing word comes before the key. The words are close/fix/resolve/complete/implement and their tense forms; ref/refs/part of only link, and skip/ignore suppress linking. Every automatic move writes a visible activity row that links to the PR, so mistakes are easy to see and undo by hand. The Actions workflow is a documented fallback for teams without org-owner access, not the main path. The GitHub App waits until Spacer has more than a handful of customer organizations, or until you want "SPC-12 moved to Done" comments on PRs and automatic redelivery.

| Phase | Scope | Exit criterion |
|---|---|---|
| 0. Task keys | Prefix + number columns and trigger, backfill, key shown in board, detail, search and notifications, "Copy branch name" button | Every task, including unfiled ones, has a stable, searchable key |
| 1. MVP webhook | Data model + Vault secret, `github-webhook` function, HMAC helper, delivery dedupe, `apply_github_event` RPC, In Progress / Done defaults, activity row + friendly bell text, Settings card with `integration.manage`, repo → project linking | A merge to `main` mentioning `SPC-12` moves it to Done exactly once, visibly attributed, on a test organization |
| 2. Hardening & fidelity | GitHub-identity linking for attribution, all-PRs-merged rule, redelivery cron via pg_cron, secret rotation with grace window, per-organization mapping UI, `in_review` status + "review requested" mapping | Redelivered and duplicate events are no-ops; review requests show In Review |
| 3. GitHub App | App registration, install callback mapping `installation.id` to the organization, PR link-back comments, automatic redelivery | One-click install replaces pasting secrets |

Five decisions block Phase 0 and Phase 1, and only the product owner can make them.

| Decision | Options | Recommendation |
|---|---|---|
| Key scope | One prefix per organization (`SPC-123`, stable when a task moves project) vs per project (`WEB-12`, changes on move) | Per organization: it covers unfiled tasks and never renumbers |
| Done with open subtasks | Mark subtasks done / refuse and log / only move tasks without subtasks | Refuse: keep the task In Progress, log "merged, N subtasks open", notify the assignee (avoids the silent client revert) |
| Unmatched GitHub user | Attribute to a "GitHub" system actor / to the admin who connected / drop the event | System actor, which means changing `can_see_activity` to allow it |
| Permission | New `integration.manage` vs reuse `organization.update` | New key: delegable without granting rename rights |
| In Review | Build the `in_review` status first vs map review to an `in_progress` custom column | Ship v1 without it; add it in Phase 2 with the already-planned migration |

Two smaller questions also need an owner: whether a revert should reopen a task (no vendor documents this; the safe default is no automatic reopen), and how PRs from forks are treated in public repos. Following GitLab's warning that external users can write closing patterns ([GitLab Docs](https://docs.gitlab.com/user/project/issues/managing_issues/)), the safe default is to act only on the merge event in the base repo, never on a PR opened from a fork.

## Conclusion

The hard part of this feature is not GitHub. The webhook plumbing is well documented, and the market convention is settled. The hard part is that Spacer's data model and audit trail assume a human with a JWT behind every change. The short task key is the real prerequisite: it also improves search, notifications and conversation in general, so it pays off even if the integration slips. The invisible activity row is the real risk, because a working integration that leaves no visible trail would erode trust in the board faster than having no integration at all.

Two habits from earlier work carry over directly. The Vault-plus-`SECURITY DEFINER` pattern behind `dispatch_edge_webhook` handles the secret problem, and the dry-run-plus-rollback migration routine fits the schema changes. The one new discipline is to treat the webhook endpoint as hostile input. That means signature first, binding to a numeric repo ID, a unique delivery ID, and one narrow RPC that does all the writing. With those in place, Phase 1 is a contained build rather than a security project.
